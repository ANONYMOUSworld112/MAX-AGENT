## 1. Transport & Auth

- **Transport:** HTTP/JSON over the local network (loopback if co-located, LAN if the Windows node is a separate physical machine).
- **Auth:** shared local token issued by the existing MAX orchestrator at node registration time, sent as a bearer token on every request. No public exposure — this API is never intended to leave the local network.
- **Versioning:** all routes prefixed `/v1/` so the contract can evolve without breaking an in-flight integration.

## 2. Endpoints

### `POST /v1/tasks`
Submit a new task to the Computer-Use Node.

```json
// Request
{
  "task_id": "uuid",          // generated by the orchestrator, not the node
  "user_request": "string",
  "goal": "string",
  "context": {                 // optional prior task memory / conversation context
    "prior_task_ids": ["uuid"]
  }
}

// Response — 202 Accepted
{
  "task_id": "uuid",
  "status": "QUEUED"
}
```

### `GET /v1/tasks/{task_id}`
Poll current task state (mirrors the `Task` schema in `TRD.md` §6).

```json
{
  "task_id": "uuid",
  "status": "RUNNING",
  "current_step": 3,
  "completed_steps": [ /* Step */ ],
  "plan": [ /* Step */ ],
  "last_verification": { /* VerificationResult */ }
}
```

### `POST /v1/tasks/{task_id}/control`
User interrupts — maps directly to `PRD.md` §7 (STOP/PAUSE/RESUME/CANCEL/SKIP/RETRY).

```json
{ "action": "STOP" | "PAUSE" | "RESUME" | "CANCEL" | "SKIP" | "RETRY" }
```

Must be processed **within one action-cycle** — the node checks for a pending control signal before every `ACT` step in the loop (`ARCHITECTURE.md` §3), not just between tasks.

### `POST /v1/tasks/{task_id}/confirm`
Resolves a `WAITING_FOR_USER` state raised by a FRIDAY-tier boundary or an Ultron-lockout gate.

```json
// Request
{
  "step_id": "string",
  "confirmed": true,
  "user_note": "string | null"
}

// Response
{ "task_id": "uuid", "status": "RUNNING" }
```

**Constraint:** the node must reject a `confirm` call for an `ULTRON_LOCKOUT`-tier step if the confirmation payload doesn't explicitly reference the exact `step_id` that was presented to the user — no blanket "confirm everything" call is accepted for lockout-tier steps, ever.

### `GET /v1/tasks/{task_id}/observability`
Live state for the dashboard (`ARCHITECTURE.md` §8): current screenshot reference, active app, detected elements, current agent, confidence, last tool call, last verification result.

### `GET /v1/health`
Node liveness/readiness check — orchestrator polls this before routing new tasks to the node.

```json
{ "status": "ready" | "degraded" | "unreachable", "active_tasks": 2 }
```

## 3. Webhooks (node → orchestrator)

Rather than the orchestrator polling continuously, the node pushes state transitions back:

```json
POST {orchestrator_callback_url}/v1/computer-use/events
{
  "task_id": "uuid",
  "event": "STATUS_CHANGED" | "WAITING_FOR_USER" | "COMPLETED" | "FAILED",
  "status": "string",
  "detail": { /* context-dependent */ }
}
```

The orchestrator's existing audit trail is the durable record — this webhook is a notification, not the source of truth. If a webhook delivery fails, the orchestrator falls back to polling `GET /v1/tasks/{task_id}`.

## 4. Error Format

```json
{
  "error": {
    "code": "NODE_UNREACHABLE | TASK_NOT_FOUND | INVALID_CONFIRMATION | PERCEPTION_FAILURE | ...",
    "message": "human-readable string",
    "task_id": "uuid | null",
    "retryable": true
  }
}
```
